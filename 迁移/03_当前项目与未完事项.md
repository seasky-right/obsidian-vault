## 1. 当前主线：智能体辅助 RPC 校正项目

**状态：当前核心主线。**

### 1.1 项目概况

项目在已有自动化 RPC 校正流程上引入大模型或智能体能力，用于：

- 对影像和场景进行较宏观的判断；
- 判断影像中是否存在云等问题；
- 当一轮结果不理想时继续尝试；
- 组织多轮工具调用与流程执行；
- 自动生成调研、分析或结果报告。

现有测试表明，智能体版本与原有自动化工具在最终校正效果上接近。项目目前最主要的增量并不是精度出现巨大提升，而是：

- 自动化程度提高；
- 可以进行多轮尝试；
- 能够组织工具执行；
- 可以根据中间结果继续决策；
- 能够自动形成报告和过程记录。

### 1.2 当前最重要的问题

用户目前最需要围绕这个项目解决的是：

- 自己实际承担了什么核心工作；
- 项目的创新点如何准确表达；
- 如何避免项目被理解成“在原有工具外面简单套一层大模型”；
- 智能体相较传统自动化流程究竟增加了什么不可替代的价值；
- 如何设计能够支持这些判断的对照实验；
- 大量实现由 AI 辅助完成后，自己是否真正理解关键代码和系统结构；
- 项目能否形成论文、竞赛成果、系统 Demo 或其他可验证成果。

### 1.3 当前应优先补足的内容

#### 系统结构

需要能够清楚说明：

- 输入是什么；
- 原有 RPC 校正工具负责什么；
- 大模型或智能体负责什么；
- 每一轮如何判断是否继续；
- 工具之间如何传递数据；
- 哪些步骤是固定流程；
- 哪些步骤由模型动态决策；
- 输出结果和报告如何生成。

#### 关键代码与数据流

不要求用户立刻掌握全部代码，但至少应掌握：

- 主程序入口；
- 智能体循环；
- 工具封装；
- 结果评价；
- 多轮重试；
- 日志与报告生成；
- 模型判断结果如何影响下一步执行。

目标不是摆脱 AI，而是避免只能描述界面和功能，却无法解释关键技术路径。

#### 对照实验

后续评价不能只使用“更智能”“更自动化”等描述，应尽量比较：

- 传统自动化版本；
- 单轮大模型版本；
- 多轮智能体版本；
- 人工干预流程。

可能需要关注：

- 最终校正效果；
- 成功率；
- 失败后的恢复能力；
- 人工操作次数；
- 总运行时间；
- 工具调用次数；
- 成本；
- 报告完整度；
- 不同场景下的稳定性。

#### 个人贡献记录

应持续记录：

- 用户具体完成了哪些模块；
- 参与了哪些技术决策；
- 解决过哪些问题；
- 做了哪些实验；
- 对原方案进行了哪些修改；
- 哪些代码虽然由 AI 生成，但经过用户设计、验证和调整；
- 哪些部分可以作为论文、答辩或简历中的个人贡献。

### 1.4 当前工作原则

- RPC 项目是目前唯一应被视为主线的项目。
- 其他学习和项目不应频繁挤占这条主线。
- 新学习内容最好直接服务于 RPC 项目，例如：
  - 为了看懂系统而学习 Agent loop；
  - 为了理解代码而补充 Python 或软件工程基础；
  - 为了评价系统而学习实验设计；
  - 为了展示项目而优化前端或报告。
- 不应因为想一次补齐所有基础，而长期停留在准备阶段。
- 也不应为了赶进度完全忽略对关键代码和架构的理解。
